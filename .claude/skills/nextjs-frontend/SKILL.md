# Next.js frontend in this project

> Visual decisions (world, tokens, components, flow rules) belong to the
> `ui-design` skill and the impeccable workflow it mandates. This skill
> covers how the frontend is built; load both for any visible change.

The site is one Next.js app (`apps/web`) that also hosts Payload. Visitors
get a server-rendered landing page that behaves like a single-page app:
in-page sections with anchors, client-side navigation to `/login`,
`/register` and `/account`, no full reloads. It is bilingual (English at `/`,
Arabic RTL at `/ar`) and themed (light/dark/system). Two constitution
principles govern every UI task: performance budgets are requirements
(Principle II) and responsive + accessible + bilingual + themed is the
definition of done (Principle VI).

## Route and module layout

```
apps/web/src/
├── app/
│   ├── (payload)/              # generated by Payload (admin + API). Do not edit.
│   └── (site)/
│       ├── globals.css         # Tailwind entry + design tokens (:root light, .dark dark)
│       ├── sitemap.ts, robots.ts
│       └── [locale]/           # 'en' served at /, 'ar' served at /ar
│           ├── layout.tsx      # <html lang dir>, fonts, ThemeProvider, NextIntlClientProvider, header, footer, WhatsApp
│           ├── page.tsx        # landing page: hero + CMS sections
│           ├── login/page.tsx
│           ├── register/page.tsx
│           ├── account/{layout,page}.tsx   # auth-protected
│           └── not-found.tsx
├── proxy.ts                    # `createMiddleware(routing)` from next-intl (Next 16 file name for middleware)
├── i18n/{routing,request,navigation}.ts
├── modules/<feature>/components/   # feature UI (landing/sections, auth/forms, contact/WhatsAppButton)
├── modules/<feature>/queries.ts    # cached CMS reads used by pages, locale-aware
├── modules/brief/                  # brief builder: option sets, briefs, submitBrief action
└── shared/{ui,ui/sign,components,theme,i18n}/  # primitives, sign kit, header/footer, ThemeToggle, LocaleSwitcher
apps/web/messages/{en,ar}.json      # every static UI string (outside src/)
```

Pages are thin: they call a module's `queries.ts`, pass data to components,
and set metadata. This is Next.js 16: `params`, `searchParams`, `cookies()`
and `headers()` are async (always `await`); request interception lives in
`proxy.ts` (not `middleware.ts`); `revalidateTag` takes a second argument
(`'max'`). Logic lives in modules; shared primitives live in
`shared/ui`. Do not import one module's internals from another; export what
is needed from the module's `index.ts`.

## Server first, client at the leaves

- Components are Server Components unless they need state, effects or
  browser APIs. Add `'use client'` to the smallest component that needs it
  (a mobile menu toggle, a form, an accordion), not to a whole section.
- Fetch CMS data only in server components via module `queries.ts`
  (wrapped in `cachedQuery` with a tag, see payload-cms skill). Never fetch
  content from the browser for first paint; it delays LCP and duplicates the
  API surface.
- Forms use Server Actions with `useActionState` for pending/error state. The
  page works without JavaScript and upgrades when it loads.
- Navigation uses `Link`, `redirect`, `usePathname` and `useRouter` from
  `@/i18n/navigation` (next-intl wrappers that keep the locale prefix), never
  `next/link` or `next/navigation` directly. After a successful action use
  the i18n `redirect()` on the server. Avoid `window.location` and manual
  reloads.

## The landing page

`app/(site)/[locale]/page.tsx` renders:

1. `Hero` from the `LandingPage` global: with `hero.layout: briefBuilder`
   (default) it shows the eyebrow, headline (seeded as "You brief. We
   shoot.") with its Arabic line, subheadline, then the `BriefBuilder`
   (`BriefBar` with `BarField` + `ResultGroup`s) and the `TopHit` row as the one primary
   action, with "Rather talk? WhatsApp us" as the secondary link; `ctas` is
   the alternative layout with two `CtaLink`s. With no photography, the
   headline or the brief panel is the LCP element, so keep both
   server-rendered; an optional hero image gets `priority` and `sizes`.
2. `RenderBlocks` over `sections` — one component per block type in
   `modules/landing/components/sections/`. Each section is a `<section>`
   with an `id` derived from its block (for `#how-it-works` style anchors) and
   a heading level that continues the document outline (`h2` for sections,
   `h3` inside).
3. Header/footer from `SiteSettings` + `LandingPage.navigation`.

Copy in sections may contain persona placeholders such as `{persona.singular}`;
render it through `interpolatePersonaCopy` from `@shoot/domain` (see the
persona-extensibility skill). Never hardcode "photographer" in JSX.

## WhatsApp call-to-action

`modules/contact/components/WhatsAppButton.tsx` builds its href with
`buildWhatsAppLink(number, message)` from `@shoot/domain/contact`, which
normalises the number to digits and URL-encodes the message. Render as an
`<a target="_blank" rel="noopener noreferrer">` with an accessible name
("Chat on WhatsApp"); the floating variant respects
`env(safe-area-inset-bottom)` and does not cover form submit buttons on
mobile. The number comes from `SiteSettings`; there is exactly one source.

## Languages and direction

- Routes live under `app/(site)/[locale]`. Pages call `setRequestLocale(locale)`
  first (enables static rendering) and read `locale` from `params` (async in
  Next 16). `generateStaticParams` returns both locales.
- **Static UI text** (nav, labels, buttons, errors, empty states) comes from
  `messages/{en,ar}.json` via `useTranslations()` in client components and
  `getTranslations()` in server components. Never type a visible English
  string in JSX; add the key to both files (a unit test fails if they
  diverge). Keys are namespaced by component (`auth.register.submit`).
- **CMS text** arrives already localised from module queries that pass
  `locale` to Payload (fallback to English is done by Payload). Components
  never choose a language themselves.
- `<html lang={locale} dir={dirFor(locale)}>` is set once in the layout.
  Everything else follows from `dir`: use only **logical** utilities
  (`ms-*`, `me-*`, `ps-*`, `pe-*`, `inset-s-*`, `inset-e-*`, `text-start`,
  `text-end`, `rounded-s-*`, `border-s-*`; `start-*`/`end-*` are deprecated
  since Tailwind 4.2). Physical `ml/mr/pl/pr/left/right` are banned by the
  lint script because each one is an RTL bug.
- Directional icons (arrows, chevrons, "next") get `rtl:-scale-x-100`.
  Non-directional icons and logos do not flip.
- Phone numbers, emails, URLs and code inside Arabic text go through the
  `Bidi` primitive (`<bdi dir="ltr">`) so digits and punctuation keep their
  order.
- Fonts (chosen with the visual direction, research §16): the system UI
  stack (`-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, system-ui,
  sans-serif`), whose Arabic companions ship with each platform; no
  `next/font` files at all, mapped in `@theme inline`; tabular figures via
  `font-variant-numeric`. Zero font bytes is part of the direction.
- The `LocaleSwitcher` links to the same path in the other locale and keeps
  the `#anchor` and `?next=`; next-intl writes the `NEXT_LOCALE` cookie. Do
  not build locale URLs by string concatenation.
- Check every change at 360 px in Arabic as well as English: RTL exposes
  overflow and alignment bugs that LTR hides.

## Theme (light / dark / system)

- Colours are **semantic tokens** declared once in `globals.css`, using
  the roles from the `ui-design` skill (`--ground`, `--ink`, `--panel`,
  `--panel-action`, `--arrow`, `--attention`) plus neutral support tokens. Tailwind
  v4 requires `@theme` to be top-level, so the pattern is: plain variables
  with light values under `:root { --ground: …; --ink: …; --panel: …; --panel-action: …; --arrow: …; --attention: … }`,
  dark values under `.dark { … }` (plus a `@media (prefers-color-scheme: dark)`
  fallback for no-JS), then one mapping
  `@theme inline { --color-ground: var(--ground); --color-ink: var(--ink); … }`.
  Components use `bg-ground`, `text-ink`, `bg-panel`, `bg-panel-action`; with
  semantic tokens almost no component needs a `dark:` class. Reach for
  `dark:` only for genuine exceptions (an image swap, the panel hairline edge).
- `ThemeProvider` (next-themes, `attribute="class"`, system default) wraps
  the app in the `[locale]` layout; `<html suppressHydrationWarning>` is
  required because the no-flash script sets the class before React hydrates.
- `ThemeToggle` is a small client island (light / dark / system) with
  accessible names from messages and `aria-pressed`. Render it only when JS
  is available; without JS the site follows `prefers-color-scheme` through
  the token fallback.
- Images that fail on dark backgrounds (site logo, partner logos) have a
  dark variant from the CMS; `CmsImage` renders both with `dark:hidden` /
  `hidden dark:block` so the swap costs no JavaScript. A logo without a
  dark variant sits on a light chip.
- Contrast is audited per token pair in both themes by a unit test; if you
  add a token, add its pair and ratio comment.
- Test in both themes: axe in Playwright's `dark` project, and a first-frame
  check that the dark background is already painted before hydration.

## Styling

- Tailwind v4: tokens (colours, spacing, radii, font sizes) are declared once
  in `globals.css` (plain variables mapped through `@theme inline`); there is no `tailwind.config.js`.
  Components use token classes, never arbitrary hex values. `globals.css` is
  imported by `(site)/[locale]/layout.tsx` only, so preflight never reaches the
  Payload admin.
- Mobile-first: write the base styles for 360 px and add `md:`/`lg:`
  overrides. Check every change at 360, 768, 1024 and 1440 px before calling
  it done; the checklist is in `references/responsive-a11y.md`.
- Keep component class lists readable: extract a primitive into `shared/ui`
  when the same combination appears three times.
- `prefers-reduced-motion` disables non-essential animation; animate only
  `transform` and `opacity`.

## Performance rules (the ones that actually move Lighthouse)

- Images: always `next/image` with `width`/`height` or `fill` + `sizes`.
  Hero gets `priority`; everything below the fold lazy-loads by default.
  Use the CMS-generated size variants; never serve the original upload.
- Fonts: none loaded; the system UI stack is the world's own voice (research
  §16), so there is no font request on the critical path.
- JavaScript: the landing page ships ≤ 200 KB compressed. Run
  `pnpm --filter web analyze` (`ANALYZE=true next build`) when adding a dependency to a client component;
  a carousel or animation library needs a justification in the plan.
- Third-party scripts: none on first paint. Analytics, if any, loads with
  `next/script` `strategy="lazyOnload"`.
- Caching: landing and settings reads are cached and tagged; Payload hooks
  revalidate on publish. Do not add `dynamic = 'force-dynamic'` to public
  pages.
- Avoid layout shift: reserve space for images, badges and async content;
  no font-swap jank thanks to `next/font`.

The full pre-merge checklist and how to run Lighthouse locally are in
`references/performance-checklist.md`.

## Accessibility baseline

Semantic landmarks (`header`, `nav`, `main`, `footer`), one `h1` per page,
labelled inputs (`<label htmlFor>`), visible focus rings, buttons for actions
and links for navigation, `aria-expanded` on toggles, alt text from the CMS
(required field), colour contrast ≥ 4.5:1. Keyboard-walk every interactive
component you touch. Details and a test checklist are in
`references/responsive-a11y.md`.

## SEO and metadata

Export `generateMetadata` on pages using `LandingPage.seo` (title,
description, OG image). Provide `sitemap.ts` and `robots.ts`. Structured
data (Organization, FAQPage when an FAQ block is present) is rendered as JSON-LD
in the page, built from CMS data.

## Testing what you build

- Component tests (Vitest + React Testing Library) for every interactive
  component and every section renderer: renders CMS data, handles empty
  arrays, interpolates persona copy, exposes the right roles and names, and
  renders correctly with `renderWithLocale(ui, { locale: 'ar' })`.
- E2E (Playwright) for the journeys: landing renders seeded content, brief
  builder → WhatsApp, WhatsApp link carries the configured number, and
  register → login → account;
  the `ar-mobile` and `dark` projects run the same smoke specs.
- Lighthouse CI runs on PRs; run it locally before pushing a UI change.

See the testing-strategy skill for configuration and conventions.
